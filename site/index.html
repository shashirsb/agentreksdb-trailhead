What's different

Not a database with agents bolted on

Most agent stacks glue half a dozen systems together and hope the glue holds. AgentreksDB starts from the agent: how it retries, what it remembers, how its loops run and who it trusts. Here is what that changes, and what it doesn't.

Built

Write on any master

Every master takes writes and tells the others. There is no single leader to wait for or fail over to.

Today the masters share one process on a simulated network. Real machines come with milestone M1.

Built

Merge by field

Two agents edit different fields of one document and both edits survive. Merge rules are set per collection.

Built

Retry without fear

Writes carry an idempotency key, so a retry stores once. Replies are receipts: how many copies, how many needed, what is waiting.

Built

Memory with a gate

Remember, recall, forget, consolidate. Memories from sources you don't trust wait in quarantine until a reviewer releases them.

Built

Events without a broker

Agents talk through the graph: an inbox with ack and nack, timers, a causal trace and a loop governor that stops runaway loops.

Built

Ask as of any day

Graph links have validity windows and memory recall can time-travel, so an agent can ask what was true then.

Built

Narrow tokens, checkable log

An agent can hand a narrower token to a sub-agent. Every admin action lands in a hash-chained audit log you can verify.

Designed

Strong where it matters

Eventual by default. Pick linearizable per collection for unique names or locks. On the cut-off side of a split, strong collections refuse.

What isn't new

Multi-master writes, hinted handoff, vector search, graphs and Iceberg all have precedent. We won't call this the first or the fastest. The difference is the combination: one engine whose interface, memory and events are made for agents, with the trade-offs written down. Speed claims wait for a benchmark anyone can rerun.

        Machines of any shape share the load fairly

        Each master carries a share of the data in proportion to its weight. A node's weight is the smallest of cores ÷ 4, memory ÷ 16 GiB, storage ÷ 256 GiB and durable writes per second ÷ 1,000, held between 0.125 and 16.         Resilience

        Built for a bad day, and honest about it

        Agents burst, loop and retry. AgentreksDB expects that. It answers "come back in a moment" instead of falling over, keeps every write it acknowledged, grows in place, and catches up a master that was away.

        • 38,449operations in the run
        • 0failed, for callers that retried
        • 27,040acknowledged writes, every one read back at quorum
        • 8,975polite "retry shortly" answers with Retry-After
        The price

        p50 337 ms, p99 2.0 s, p99.9 5.0 s while overloaded. Nothing was lost and nothing failed, but callers waited. Overload costs latency, never data.

        Release binary on 2 cores: 100 requests a second, then 10×, then 30×, with the CPU limit changed mid-run. "No errors" means no lost acknowledged write, no crash and no failed operation for a caller that retries. It is a stress test, not a benchmark.

        Built

        Away masters catch up

        Writes meant for an offline master wait as hints and replay when it returns. Read repair and digest repair mop up the rest.

        Built

        Drain, don't drop

        On shutdown the server stops taking new work, finishes what is in flight and reports not-ready so traffic moves away. Health, ready and metrics ports are built in.

        Written

        Grows in place

        The controller resizes CPU and memory without a restart, grows volumes at 70% full and waits ten minutes before shrinking. Not yet run on a real cluster.

        Designed

        Slow beats stopped

        If a nearby voter fails, strong writes will carry on at the far master's slower speed instead of stopping, and say so. Times are modelled, not measured.

        Storage Optional build

        Data moves downhill into Iceberg on S3

        Fresh data lives on your masters, where agents read and write it. When it settles, move it to Apache Iceberg tables on S3 for analytics and archive. The lakehouse export is an optional build of the engine, with its own page in the console.

        • 1Agents write to any master. New data is the warmest data.
        • 2Older data moves to Iceberg on S3. You decide what moves and when.
        • 3Iceberg is an open table format, so other tools can read it without a copy job.

        Agents talk through the database, not a broker

        Agent systems have been climbing for a while. AgentreksDB is built for the last step: long-running, asynchronous agents in loops that keep improving, working on a graph and talking to each other through it.

        The change is the message

        • 1Long-running. Agents keep working for hours or days, not one request at a time.
        • 2Asynchronous. An agent watches the graph, picks up a change when it is ready and writes its result back.
        • 3Continuously improving. Results feed the next pass of the loop, so every round starts from better data.
        • 4No broker. Agents talk through AgentreksDB instead of a separate message queue.

        Said plainly

        • All masters share one process today. Separate machines cannot form a cluster until M1.
        • Client traffic is plain HTTP unless a proxy ends TLS. Mutual TLS between masters arrives with M1.
        • Speed is early: about 54,000 writes a second with operating-system durability, about 4,000 with a flush on every commit, and about 83,000 point reads a second, on a 2-core test box with one thread. The project's own notes call that "not competitive yet".
        • The deploy kit has not yet run against a real cloud account or cluster.
        • Time series is not wired to the API yet.
        • AgentreksDB has not been compared with another database yet. "Fastest" waits for the harness above.
