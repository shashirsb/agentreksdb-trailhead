# Security policy

## Reporting a vulnerability

Use either channel. Both are private.

- **GitHub private vulnerability reporting** (preferred): on the affected repository, open the **Security** tab
  and choose **Report a vulnerability**. This creates a private draft advisory that only you and the security
  responders can see, and it is where the advisory and any CVE request are prepared.
- **Email security@agentreks.dev** if you would rather not use GitHub, or if the report concerns GitHub itself.

Do not file a public issue or intent for an unfixed vulnerability: intents and their chats are public and
permanent.

Include what is affected (AgentreksDB, Trailhead, a deploy kit or the pipeline itself), how to reproduce it, and
the impact you expect. We acknowledge within 3 working days and give a first assessment within 10.

## Severity

We score every accepted report with **CVSS 4.0** and publish the full vector string with the advisory.

| Band | CVSS 4.0 base score |
| --- | --- |
| Critical | 9.0 – 10.0 |
| High | 7.0 – 8.9 |
| Medium | 4.0 – 6.9 |
| Low | 0.1 – 3.9 |
| None | 0.0 |

**Pipeline integrity is raised one level.** Anything that lets code reach main without being generated by the
pinned model through the Trailhead pipeline — a bypass of the attestation gate, a forged provenance statement, a
way to make the commit workflow apply a bundle that the ledger does not match, a way to get a human-written diff
merged — is treated as one severity band above its CVSS score, capped at Critical. The AI-only invariant
(CHARTER.md section 4) is the project's central claim; a hole in it is worse than its score suggests.

## Fix SLAs

Calendar days from our first assessment to a fix merged in main.

| Severity | Fix within |
| --- | --- |
| Critical | 7 days |
| High | 30 days |
| Medium | 60 days |
| Low | 90 days |

If we are going to miss an SLA we tell the reporter why and name a new date. Missed SLAs are recorded in the
ledger with the reason.

## Supported versions

| Version | Status |
| --- | --- |
| `main` | Supported. The only supported version today. |
| 0.1.x (pre-release) | Supported only as `main`; there are no tagged releases yet, so there is nothing older to patch. |

The project is pre-1.0 and has produced no release. From 1.0 the policy is: the latest minor version gets
security fixes, and the previous minor keeps getting them for 90 days after its successor ships. Fixes are
delivered as a new patch release on a supported minor, never as a private patch.

## Disclosure

We follow coordinated disclosure. A report becomes public at **the fix shipping plus 30 days, or 90 days from
the report, whichever is later**. The reporter may always publish earlier on their own initiative; we will not
ask them not to.

An extension past that date requires a governor vote, carries a public reason, and **may never take the total
past 180 days from the report**. There is no indefinite embargo.

After the fix ships, the advisory, the fix intent and its full prompt log are published, and the reporter is
credited unless they ask not to be. Every fixed vulnerability also gains a **regression test** that fails
without the fix, so the same hole cannot return unnoticed.

## Regulatory reporting we track

The EU Cyber Resilience Act (Regulation (EU) 2024/2847) introduces reporting duties for *actively exploited*
vulnerabilities from **11 September 2026**: an early warning within 24 hours and a fuller notification within 72
hours to ENISA and the relevant CSIRT, with a later final report. The regulation provides lighter obligations
for open-source software stewards than for commercial manufacturers.

Whether, and in what form, these duties apply to this project is not settled — it depends on how the project is
eventually organised (CHARTER.md section 6 contemplates a neutral nonprofit), whether it is treated as a
steward, and on guidance that is still being issued. We state no legal conclusion here. We track the regulation,
and we will comply with whatever applies to us when it applies. Practically: if we learn a vulnerability in
AgentreksDB or Trailhead is being actively exploited, we treat the 24-hour and 72-hour clocks as live from that
moment and notify, rather than waiting to settle the legal question first.

## How security fixes are made

Security fixes are generated by the pinned model like every other change, but through a private security intent
that becomes public when the advisory is published. Security fixes may merge outside the weekly train with the
approval of two governors. Every such merge is recorded in the ledger with its reason.

The embargo delays the payload, never the record. The ledger entry for an embargoed security intent is written
immediately with the payload's hash, the category, the reason, the planned release date and the approver, so the
existence of the work is public from the first minute; only the words wait. See docs/TRANSPARENCY.md.

## Kill switch

Two governors acting together can freeze Trailhead: stop generation, stop merges and stop new sign-ups. The kill
switch uses credentials separate from the model API keys and is tested monthly. Every use is recorded in the
ledger.

## Key rotation

Model API keys, the GitHub App private key, webhook secrets and the ledger checkpoint key are rotated at least
every 90 days and immediately after any suspected exposure. Rotations are recorded in the ledger (never the key
values). Commit signing is keyless (Sigstore), so there is no long-lived signing key to rotate.

## Scope of the pipeline

Reports about the pipeline are as welcome as reports about the database, including: ways to make code reach main
without the pinned model, ways to bypass a gate, ways to get secrets or network access inside the generation
sandbox, ways to forge provenance, and ways to drain the inference budget.
