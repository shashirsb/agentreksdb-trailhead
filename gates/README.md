# Trailhead gates for AgentreksDB

These files turn the `shashirsb/agentreksdb` repo into one where code reaches `main` only through the
Trailhead pipeline: generated by the pinned model, signed by the pipeline, proven by tests and policy,
and merged in the weekly train after a governor decision.

| File | Gate | Blocks merge? |
| --- | --- | --- |
| `.github/workflows/gate-tests.yml` | fmt, clippy `-D warnings`, nextest (unit + property), doc tests, coverage ratchet, cargo-mutants on changed code (≥ 80% caught) | yes |
| `.github/workflows/gate-perf.yml` | instruction counts on every PR (> +2% fails); wall-time macro suite on a bare-metal runner behind `perf:macro` and nightly | instructions: yes · macro: when labelled |
| `.github/workflows/gate-diff-policy.yml` | diff manifest → `trailhead policy check`, semgrep, cargo-deny, cargo-audit, gitleaks; SARIF upload; signed-ready `gate-verdict.json` artifact | yes |
| `.github/workflows/gate-attestation.yml` | every commit gitsign-signed by the Trailhead workflow identity, with `Generated-By`, `Spec-Hash`, `Trailhead-Intent` trailers | yes |
| `.github/workflows/gate-ai-review.yml` | PR-Agent review by a non-Claude model, reading the spec and prompt log | no — advice for the governor |
| `.github/workflows/train-gate.yml` | merge only with `train/<current>` + `decision:merge`; Sunday/Friday 00:00 PT tick to the Trailhead API | yes |
| `.github/workflows/close-human-prs.yml` | closes PRs not opened by the Trailhead App, pointing to Trailhead | — |
| `diff-policy.toml` | BLOCK/WARN rules read by `trailhead policy check` | — |
| `semgrep/rust-trailhead.yml` | semantic Rust rules (egress, processes, secret env, embedded files, Trojan Source, hostname gates) | — |
| `CODEOWNERS` | human-only paths: tests, CI, gates, build scripts, lockfile, crypto/auth/net, governance | — |
| `rulesets/main.json` | the `main` branch ruleset | — |
| `coverage-floor.txt` | coverage ratchet floor; it may rise, never fall | — |

## Gate ordering

`gate-diff-policy / policy` runs first and everything that compiles PR code waits for it. Diff-policy
is the only gate aimed at malice, so it must judge a change before a runner builds it. Because the
gates live in separate workflow files, `gate-tests` and `gate-perf` each open with a `wait-for-policy`
job that polls the checks API (read-only `GITHUB_TOKEN`) for the `gate-diff-policy / policy`
conclusion on the same SHA; every other job in those files `needs:` it. It fails closed — unknown,
pending past the 25-minute budget, failed, cancelled or skipped all stop the workflow — so renaming
the diff-policy job without updating the `CHECK_NAME` env in both files blocks the pipeline rather
than quietly skipping the barrier. `gate-attestation` only reads commit metadata and signatures, so
it does not wait.

## The coverage ratchet

`coverage-floor.txt` is a one-way ratchet: **it may only ever be raised, never lowered.** The floor is
currently `60.0`. A PR that pushes coverage above `floor + 0.5` prints a notice inviting the floor to
be raised to match; lowering it is not a routine change but an admission that the project is giving up
ground, and since `/gates/` is CODEOWNED it takes a human governor's approval either way. A missing
`coverage-floor.txt` fails the gate instead of defaulting to `0.0` — deleting the file must not be a
way to switch the gate off. `0.0` is not a valid floor in practice: it disables the gate while leaving
it looking enabled.

## Install

From a checkout of `agentreksdb` (paths assume the Rust workspace lives in `agentreksdb/`; set the
repository variable `WORKSPACE_DIR` if it moves):

```bash
TH=../agentreksdb-trailhead/gates
mkdir -p .github/workflows gates/semgrep gates/checks
cp $TH/.github/workflows/*.yml .github/workflows/
cp $TH/CODEOWNERS .github/CODEOWNERS
cp $TH/diff-policy.toml $TH/coverage-floor.txt $TH/invariants.toml gates/
cp $TH/semgrep/rust-trailhead.yml $TH/semgrep/sabotage.yml gates/semgrep/
# The sabotage checks: environment invariance, magic-value triggers, syscall capability diff,
# honeytokens, the security-invariant registry and the obfuscation scan. See gates/checks/README.md.
cp $TH/checks/*.py gates/checks/
# Benchmarks and fuzz targets the perf and fuzz gates measure. Both are scaffolds with the
# oracles already written: the entry points are stubbed and marked, and until they point at the
# real code the gates run but prove little. See gates/templates/fuzz/README.md.
mkdir -p benches fuzz && cp $TH/templates/benches/iai.rs benches/
cp -r $TH/templates/fuzz/. fuzz/
# This install commit is human-authored, so it is the one commit that goes in before the ruleset:
git add .github gates && git commit -s -m "Install Trailhead gates" && git push
gh api -X POST repos/shashirsb/agentreksdb/rulesets --input $TH/rulesets/main.json
```

## Repository settings

Variables: `WORKSPACE_DIR` (default `agentreksdb`), `TRAILHEAD_URL`, `TRAILHEAD_BOT_LOGIN` (the App's bot
login, e.g. `agentreks-trailhead[bot]`), `TRAILHEAD_IDENTITY_REGEXP` (only if the signing workflow path
changes), `REVIEW_MODEL`, `BENCHER_PROJECT`, `TRAILHEAD_VERIFIER_IMAGE`.

Three of those are load-bearing for security, and each fails closed:

- `TRAILHEAD_VERIFIER_IMAGE` **must be pinned by digest**, e.g.
  `ghcr.io/shashirsb/agentreksdb-trailhead@sha256:<64 hex>`. A mutable tag such as `:main` is rejected
  and `gate-diff-policy` fails: that container is handed the whole PR worktree, so the bytes that judge
  a diff have to be fixed. Resolve a digest with
  `docker buildx imagetools inspect <image>:<tag> --format '{{.Manifest.Digest}}'` and bump the variable
  whenever the verifier is rebuilt.
- `TRAILHEAD_BOT_LOGIN` must be set, or `close-human-prs` does nothing. Left empty it would compare
  every author against `''` and close the pipeline's own pull requests, so the workflow now requires it.
- `TRAILHEAD_URL` also fixes the only host `gate-ai-review` will fetch a prompt log from: the PR body's
  `Prompt-Log:` line must match `https://<that host>/api/intents/<digits>` exactly or it is rejected
  unfetched.

Secrets: `TRAILHEAD_TICK_TOKEN` (bearer token the API accepts on `/api/train/tick`), `OPENAI_KEY` (the
reviewer model — a different family from the generator), `BENCHER_API_TOKEN`.

Runner: register one self-hosted runner labelled `perf-bare-metal` on a dedicated machine (fixed CPU
governor, SMT off, `isolcpus`, ASLR off) for the macro benchmarks.

## Required checks

Mark these as required (the ruleset already lists them): `gate-tests / static`, `gate-tests / nextest`,
`gate-tests / coverage`, `gate-tests / mutants`, `gate-perf / instructions`, `gate-diff-policy / policy`,
`gate-attestation / verify`, `train-gate`.

Not required: `gate-ai-review / pr-agent` (advisory), `gate-perf / macro` (runs only when labelled).

## Notes before turning enforcement on

- Every `uses:` is pinned to a full 40-char commit SHA with the version in a trailing comment, the
  gitleaks release is verified against a pinned sha256 before it is unpacked, semgrep is installed at an
  exact version, and the verifier container must be digest-pinned. **One exception remains:**
  `sigstore/gitsign-installer@main` in `gate-attestation.yml` could not be resolved to a SHA (the
  repository does not answer under that name) and is marked `TODO(pin): unresolved`. The resolvable
  alternative is `chainguard-dev/actions/setup-gitsign@8f31e9482b447ff2c69eca944a09b4b31a4a85d0`
  (v1.7.2); switching changes which third party installs the signature verifier, so it is a governance
  decision. Pin or replace it before marking `gate-attestation / verify` required.
- Tags and branch refs must never come back. `dtolnay/rust-toolchain` was selected by its ref
  (`@stable`); pinned by SHA that ref no longer names a toolchain, so every use of it now states
  `toolchain: stable` explicitly rather than resting on the action input's default.
- `gate-tests / mutants` fails closed. `cargo mutants` exit codes 0, 2 and 3 mean the run completed and
  are scored against the 80% threshold; any other exit code (usage error, baseline build or test
  failure, OOM, signal) fails the gate, as does a missing or unreadable `outcomes.json`. The old
  `|| true` plus "exit 0 if the report is absent" meant a crashed mutation run read as a pass. Timed-out
  mutants no longer count as caught: the threshold is `caught / (caught + missed + timeout)`, and both
  that and the looser caught-or-timeout rate are printed.
- `gate-ai-review` is advisory, is not a required check, and has no merge authority. It never applies a
  decision label — its label features are off and `issues: write` is not granted — because
  `pull-requests: write` cannot be narrowed to exclude labels. `decision:merge` and `train/<week>` must
  only ever come from the Trailhead App. It also forwards only the structured spec fields
  (`requirements`, `acceptance_tests`, `affected_areas`, `out_of_scope`), wrapped in a per-run random
  delimiter and labelled as data; contributor free text (`messages`, `clarification_log`) is dropped
  before the prompt is built.
- The ruleset does NOT use GitHub's `required_signatures`: GitHub does not recognise Sigstore (gitsign)
  signatures, so it would refuse every Trailhead commit. `gate-attestation` (a required check, pinned to
  GitHub Actions via `integration_id`) verifies them instead, and the merge queue uses MERGE (not squash or
  rebase) so the signed commits land on `main` unchanged. The only merge commits allowed are GitHub's own.
- `required_approving_review_count` is **1**, combined with `require_code_owner_review`. A label is not
  merge authority: with a count of 0 the entire human decision was the `decision:merge` label, so
  anything that could write a label could merge. A human must now press Approve on every change.
  **The governors team must therefore be the CODEOWNER** in `.github/CODEOWNERS` — GitHub only requires
  that the approval come from *a* code owner, so the approving review is a governor's only if the owner
  entries name the governing body. Point every rule in `CODEOWNERS` at the governors team (e.g.
  `@shashirsb/governors`) rather than an individual account; an individual owner makes the gate a
  single person's approval, and `dismiss_stale_reviews_on_push: true` means a new push always needs a
  fresh one. `train-gate` still enforces the train window and `decision:merge` on top of the approval —
  the label schedules a merge, the review authorises it.
- Merge queues exist only for organization-owned repos. On a personal account, drop the `merge_queue`
  rule (`deploy/gcp/setup.sh` does this automatically); Trailhead then merges directly, and all required
  checks still apply. Move the repos to a GitHub organization to get batched merges.
- `bypass_actors` is empty on purpose, including for org admins. Changing it is a governance decision and
  shows in the ruleset history.
- Add `benches/iai.rs` (iai-callgrind) to the workspace so the instruction-count gate measures something;
  until then it warns and passes.

## Supply chain, CodeQL and the security policy

Three files were added after the gates above, covering the part of a change that is not in its diff.

| File | Gate | Blocks merge? |
| --- | --- | --- |
| `.github/workflows/gate-supply-chain.yml` | zizmor on `.github/` changes, OSV-Scanner, `cargo-deny check advisories bans licenses sources`, cargo-vet on lockfile changes, the lockfile delta check, gitleaks + trufflehog `--only-verified` | yes (`cargo-vet`: see below) |
| `.github/workflows/gate-codeql.yml` | CodeQL for Rust, `security-extended`, blocking at CVSS 7.0 and above | yes |
| `SECURITY.md` | how to report a vulnerability in AgentreksDB, the CVSS 4.0 scale, the fix SLAs and the CRA clocks | — |

Both workflows open with the same `wait-for-policy` barrier as `gate-tests` and `gate-perf`, for the
same reason: every job in them resolves, builds or points a third-party scanner at PR content, so
`gate-diff-policy / policy` must have concluded `success` on the same SHA first. The `CHECK_NAME`
env in these two files has to stay in sync with the diff-policy job name along with the others.

Add to the install step:

```bash
cp $TH/SECURITY.md .github/SECURITY.md
# cargo-audit reads .cargo/audit.toml, not deny.toml, and it runs with working-directory
# $WORKSPACE_DIR — so the file belongs next to the deny.toml it mirrors, not at the repo root.
mkdir -p $WORKSPACE_DIR/.cargo && cp $TH/../.cargo/audit.toml $WORKSPACE_DIR/.cargo/audit.toml
```

### Why `.cargo/audit.toml` exists

`gate-diff-policy` runs both `cargo deny check` and `cargo audit --deny warnings`. They read the
same RustSec database and different configuration: cargo-deny reads `deny.toml`, cargo-audit reads
`.cargo/audit.toml` and ignores `deny.toml` entirely. Without that file, every advisory the
governors had already accepted in `deny.toml` was still fatal to cargo-audit, so the audit step
failed on every pull request whatever the change contained — and a gate that is always red is a gate
nobody reads.

cargo-audit is kept rather than dropped, even though cargo-deny's `advisories` check overlaps it:
two independent implementations fail differently, and `--deny warnings` also catches yanked and
unmaintained crates. The cost is two ignore lists that can drift, so the drift is now checked —
`gate-diff-policy` compares the two lists and fails if they disagree, before the audit runs. Add an
advisory to both files in the same change, with the reason, or neither.

### Required checks

Add to the required list: `gate-supply-chain / zizmor`, `gate-supply-chain / osv-scanner`,
`gate-supply-chain / cargo-deny`, `gate-supply-chain / lockfile-delta`,
`gate-supply-chain / secrets`, `gate-codeql / analyze`.

**Leave `gate-supply-chain / cargo-vet` out of the required list until `supply-chain/` exists.** The
job fails, loudly and with the `cargo vet init` commands, when a change touches the dependency graph
and there is no audit set — because a green tick meaning "not configured" is indistinguishable from
one meaning "audited", which is worse than a red one. Until the audit set is committed that failure
should be visible without wedging the pipeline, so run it unrequired; add it to the required list in
the same change that lands `cargo vet init`.

### Notes on these two gates

- **Everything is pinned, including the tools.** `taiki-e/install-action` is itself pinned by SHA and
  verifies each tool against a sha256 in its own pinned manifest, so `tool: zizmor@1.31.1` is a
  checksummed install rather than a download of whatever is newest. gitleaks and trufflehog are not
  in that manifest, so their release tarballs are checked against a sha256 pinned in the workflow
  before anything is unpacked. trufflehog is installed this way rather than through its own GitHub
  Action on purpose: that action runs `ghcr.io/trufflesecurity/trufflehog:latest`, a mutable tag,
  which is the thing the pinning rule exists to prevent.
- **OSV-Scanner exit code 128 is a failure, not a pass.** 128 means "no packages found", which is
  not "nothing is wrong" but "I had nothing to look at" — a moved `Cargo.lock`, a `WORKSPACE_DIR`
  pointing somewhere empty. Treated as success it would be the most useful exit code an attacker
  could ask for: hide the lockfile from the scanner and the dependency gate reports green forever.
- **zizmor runs offline.** Its online audits (`known-vulnerable-actions`, `stale-action-refs`) query
  the GitHub API, which would make a blocking gate depend on a third-party service being up and
  would hand a token to a tool whose input is attacker-controlled YAML. The cost is real and worth
  stating plainly: **a known-vulnerable action version is not caught by this gate.** What is caught
  is the unpinned or newly-floating `uses:`, which is static. Reviewing action versions stays a
  governor's job.
- **The lockfile delta check asks the day-one questions.** cargo-deny, cargo-audit and OSV all ask
  "is this crate known to be bad", and on the first day of an attack the answer is always no. The
  `lockfile-delta` job instead reports, for every newly added crate, how many days ago it was
  published, how many owners can publish it, and its Damerau-Levenshtein distance to a name the
  project already trusts — `rand_core` against `rand-core`, `tokio-util` against `tokio_util`. It
  blocks on a release under 30 days old, on a single owner of a crate under a year old, on a yanked
  version, and on a name within distance 2 of a trusted one (crates.io treats `-` and `_` as
  interchangeable, so a squatter does not even need a typo). Accept one of these deliberately by
  saying so in the intent and recording the crate in `deny.toml`, not by relaxing the thresholds.
  If crates.io cannot be read the crate counts as unproven and the job fails: the whole purpose of
  the job is that metadata.
- **CodeQL's verdict is computed from the SARIF, not left to the Security tab.**
  `github/codeql-action/analyze` uploads findings and then succeeds, which is reporting rather than
  gating. The SARIF is therefore also written to disk and scored in the workflow: anything at
  `security-severity` 7.0 or above fails the job, medium and low print as notices. A missing or
  unparseable SARIF fails closed — CodeQL reporting nothing is indistinguishable from CodeQL having
  been quietly switched off. The analysis uses `build-mode: none`, so this gate never executes a
  PR's `build.rs`; `languages: rust` is requested explicitly because CodeQL's autodetection
  deliberately will not enable Rust on its own.
- **One version of `codeql-action` across the repository.** These files and the SARIF uploads in
  `gate-diff-policy` all pin v3.39.1. A v4 exists; bump every gate in one change or none, because
  two majors of `codeql-action` in one repository is how a gate ends up analysing nothing.
- **`gate-ai-review` is split into two jobs.** `context` fetches and sanitises the contributor-written
  spec with `permissions: {}` — no token, no API key, nothing to steal and nothing to write with —
  and `review` holds the model key and the one `pull-requests: write` scope but never reads the PR
  body and never fetches a URL. A job that both reads attacker text off the network and holds
  credentials is the whole bug class, so the two capabilities are kept apart. The fetch also refuses
  redirects now: a URL on the right host answering `302` to somewhere else turned the host
  allow-list into nothing.
- **The reviewer's JSON verdict is data, not a decision.** Its `recommendation: merge|hold|reject`
  is a reading aid for a human governor. Nothing may parse it into a label, a check conclusion, an
  approval or an input to `train-gate`. Wiring it into the merge path would hand merge authority to
  whoever can write text into an intent, which is anyone.
- **`sigstore/gitsign-installer` still does not resolve** — the repository does not answer under that
  name, so the `TODO(pin): unresolved` in `gate-attestation.yml` stands. On the Trailhead side, where
  the same installer was referenced as `chainguard-dev/actions/setup-gitsign@main`, it is now pinned
  to `8f31e9482b447ff2c69eca944a09b4b31a4a85d0` (v1.7.2). Switching `gate-attestation` to the same
  Chainguard action changes which third party installs the signature verifier, so it stays a
  governance decision rather than a silent edit — but it is the only resolvable option, and it must
  happen before `gate-attestation / verify` is marked required.
