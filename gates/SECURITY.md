# Security policy

This is the security policy for **AgentreksDB**, the database. It is installed here by the Trailhead
gates (see `gates/README.md` in `agentreksdb-trailhead`). Trailhead — the pipeline that generates
every change in this repository — has its own policy in its own repository, and the two are kept
consistent on purpose: the same severity scale, the same SLAs, the same disclosure clock. If you
think you have found a hole in the *pipeline* rather than in the database, report it the same way
and say so; it reaches the same responders.

One thing to know before you read further, because it changes what a vulnerability report means
here: **no human writes code in this repository.** Every change is generated by one pinned model
from a public intent, signed by the pipeline, and merged only after a set of automated gates pass
and a human governor approves. So a report can be about the database, or about the machinery that
decides what gets into it, and the second kind is usually the more serious.

## Reporting a vulnerability

Use either channel. Both are private.

- **GitHub private vulnerability reporting** (preferred): open the **Security** tab on this
  repository and choose **Report a vulnerability**. That creates a private draft advisory visible
  only to you and the security responders, and it is where the advisory and any CVE request are
  prepared.
- **Email security@agentreks.dev**, if you would rather not use GitHub, or if the report concerns
  GitHub itself.

**Do not open an intent, an issue or a pull request for an unfixed vulnerability.** Intents and
their full prompt logs are public and permanent — that is the point of the project — so filing one
publishes the vulnerability. A pull request would be closed unread by `close-human-prs` anyway.

Include what is affected, how to reproduce it, and the impact you expect. We acknowledge within
3 working days and give a first assessment within 10.

We will not pursue anyone who reports in good faith through these channels, including if you
tripped over something while testing. Please do not run denial-of-service tests against hosted
infrastructure, and do not access data that is not yours.

## Severity

Every accepted report is scored with **CVSS 4.0**, and the full vector string is published with the
advisory. The vector matters more than the number: it is what lets someone else disagree with our
score.

| Band | CVSS 4.0 base score |
| --- | --- |
| Critical | 9.0 – 10.0 |
| High | 7.0 – 8.9 |
| Medium | 4.0 – 6.9 |
| Low | 0.1 – 3.9 |
| None | 0.0 |

### Pipeline integrity is raised one band

**Anything that lets code reach `main` without being generated by the pinned model through the
Trailhead pipeline is treated as one severity band above its CVSS score, capped at Critical.**

That covers, for example: a way to get a human-written commit past `gate-attestation`; a forged
provenance statement or `Generated-By` trailer; a way to make the commit workflow apply a bundle the
public ledger does not match; a way to make a gate report success without running (a scanner given
nothing to scan, a verdict file that does not parse, a required check that silently skips); a way to
write the `decision:merge` or `train/<week>` label from anything other than the Trailhead App; a way
to move a tag, digest or action reference that one of the gates runs.

The reason for the uplift is that CVSS scores impact on the running database, and these bugs do not
have that shape. Their impact is that the project's central claim stops being true, and that every
other control in this repository rests on it: the gates are what the governance is made of. A CVSS
vector has no field for "the thing that decides what is trustworthy was not trustworthy".

## Fix SLAs

Calendar days from our first assessment to a fix merged in `main`.

| Severity | Fix within |
| --- | --- |
| Critical | 7 days |
| High | 30 days |
| Medium | 60 days |
| Low | 90 days |

Security fixes are generated by the pinned model like everything else, through a private security
intent that becomes public when the advisory is published. They may merge outside the weekly train
with the approval of two governors, and every such merge is recorded in the ledger with its reason.

If we are going to miss an SLA we tell the reporter why and name a new date. Missed SLAs are
recorded in the ledger with the reason, because an SLA nobody records is a wish.

Every fixed vulnerability also gains a regression test that fails without the fix. In a project
where tests are the specification, a fix with no test is not finished.

## Supported versions

| Version | Status |
| --- | --- |
| `main` | Supported. The only supported version today. |
| 0.1.x (pre-release) | Supported only as `main`. There are no tagged releases, so there is nothing older to patch. |

AgentreksDB is pre-1.0 and has produced no release. Running it against data you care about is not
advisable yet, and no version of it is fit for production.

From 1.0 the policy is: the latest minor version receives security fixes, and the previous minor
keeps receiving them for 90 days after its successor ships. Fixes are delivered as a new patch
release on a supported minor, never as a private patch to one user.

## Disclosure

We follow coordinated disclosure. A report becomes public at **the fix shipping plus 30 days, or
90 days from the report, whichever is later**. The reporter may always publish earlier on their own
initiative, and we will not ask them not to.

An extension past that date requires a governor vote, carries a public reason, and may never take
the total past **180 days** from the report. There is no indefinite embargo.

After the fix ships, the advisory, the fix intent and its full prompt log are published, and the
reporter is credited unless they ask not to be. The embargo delays the payload, never the record:
the ledger entry for an embargoed security intent is written immediately with the payload's hash,
the category, the reason, the planned release date and the approver, so the existence of the work is
public from the first minute. Only the words wait.

## Regulatory reporting we track

The EU Cyber Resilience Act (Regulation (EU) 2024/2847) introduces reporting duties for *actively
exploited* vulnerabilities from **11 September 2026**:

- an **early warning within 24 hours** of becoming aware of active exploitation, to the relevant
  CSIRT and ENISA;
- a **fuller notification within 72 hours**, with the assessment and any corrective or mitigating
  measures;
- a **final report** later, once the vulnerability is remediated.

The regulation sets lighter obligations for open-source software stewards than for commercial
manufacturers. Whether, and in what form, these duties apply to this project is not settled: it
depends on how the project is eventually organised, whether it is treated as a steward, and on
guidance that is still being issued. **We state no legal conclusion here.**

What we do in practice does not wait on that question. If we learn that a vulnerability in
AgentreksDB is being actively exploited, we treat the 24-hour and 72-hour clocks as live from that
moment and notify, rather than settling the legal argument first. A deadline you only start once
you are certain it applies to you is a deadline you miss.

The severity uplift above interacts with this deliberately. A pipeline-integrity bug is raised one
band, and if it is being actively exploited it is also on the 24-hour clock — so the class of bug
this project is most worried about is the class with the shortest fuse.

## Scope

In scope, and as welcome as a report about the storage engine:

- the database itself — query handling, storage, replication, consistency, authentication,
  authorization, the network protocol, memory safety;
- the gates in `.github/workflows/` and `gates/` — any way to make one pass without having checked
  what it claims to check, or to make a required check not run;
- the attestation chain — commit signatures, provenance trailers, the ledger, the pinned model
  identity;
- the merge path — the branch ruleset, the train gate, the decision labels, CODEOWNERS.

Out of scope: reports that amount to "pre-1.0 software has bugs"; missing hardening with no
reachable impact; results from automated scanners with no analysis attached; and social engineering
of governors or contributors.

## A note on the gates

If your report is that a gate can be made to pass without doing its job, say so plainly and we will
treat it as pipeline integrity. The gates are the only thing standing between a generated patch and
`main`, and they are themselves generated and reviewed like any other code — which means they can
be wrong, and that a convincing-looking gate that checks nothing is a realistic failure. Reports of
that kind are the most valuable ones this project can receive.
